# 관찰 온톨로지 개편 — `observation-v1`

- 기준일: 2026-10-19
- 상태: **계획 승인, 미구현.** 사용자가 1단계(정합성)와 2단계(주장 형태 축·유형 재정비·시간
  정밀도·기존 데이터 전환)를 포함한 전체 개편 계획 작성을 요청했다. 구현·라이브 배포·라이브
  데이터 전환은 각각 별도 승인 단계다.
- 순서: [임베딩 자동 생성](embedding-auto-index.md) 다음 구현 대상.
- 선행 구조 개선: [데이터 모델·온톨로지 근본 개선](data-model-integrity.md). 기록 생애주기·근거·
  정의 저장소 규칙을 그 계획이 정하고, 관계 평가 분리(M8)는 이 계획 2단계와 같은 배포 창에서 한다.
- 공통 계약: [기록 정체성·계보·시간 계약](record-lifecycle-contract.md). 교차 유형·분할 계보,
  원본 참조와 canonical resolution, revision 상태와 시간상 현재 여부는 이 계약을 따른다.
- 선행 계약: [즉시 저장 메모리](save-first-memory-schema.md),
  [관계 온톨로지 relationship-v1](relationship-ontology.md), [온톨로지 정의](../specs/ontology-design.md)

### 2026-10-22 검토 반영

기존 F1–F15, OV01–OV12와 결정·진단 이력은 보존한다. 아래 변경은 M8 평가 분리, 시간 정밀도,
v2/v3 전환의 계획 정합성을 보완한다. 문서 정리는 구현·라이브 배포·개인 기록 전환의 완료나
추가 승인을 뜻하지 않는다. 검색의 query embedding·모델 호환성·검색 이유 정확성은
[실행 로직 정합성 계획](runtime-correctness.md)이 소유하고, 이 계획은 형태·시간·역할 정보를
해당 검색 계약에 전달한다.

## 0. 범위

포함:

- 관찰 유형·참여자 역할·주체의 정의와 버전, 쓰기 검증과 레지스트리의 정합(1단계)
- 관찰의 주장 형태 축, 관찰 유형 재정비, 프로필 사실 경계, 날짜 정밀도(2단계)
- 위 변경에 맞춘 기존 라이브 기록의 개별 전환과 에이전트(Hermes) 연동 갱신

제외(기존 결정 유지):

- 약속·만남·일정·알림 추적(관계 온톨로지 D05). 아래 `event` 형태는 이미 일어난 일을 기록할 뿐
  일정 관리 기능이 아니다.
- 조직을 별도 엔티티로 만드는 것, 두 사람 관계 전용 화면, 관계 타임라인, 시점 조회, 충돌 해결 모델
- 민감도·AI 사용 정책의 부활, 저장 전 승인 큐, Kinlayer 코어 안의 LLM 분류

관계 온톨로지 계획의 보류 목록 중 "observation regrouping"과 "`user_feeling` 분류 수정"은
이 계획이 다룬다. 나머지 보류 항목은 그대로 보류다.

## 1. 진단 (2026-10-19 라이브 읽기 전용 조회)

관계 유형(`relationship-v1`)은 한국어 정의, 방향, 역방향 표시명, 속성 스키마, 쓰기 지원 상태, 버전을
갖추고 있다. 반면 관찰 쪽은 유형 이름만 있고 의미 정의가 없어 분류가 흔들린다. 아래 수치는
활성 관찰 240건 기준이다. 개인 내용은 기록하지 않는다.

| ID | 문제 | 근거 |
| --- | --- | --- |
| F1 | 관찰 유형에 정의·포함/제외 기준·예시·버전이 없다 | 라이브 `allowed_observation_types.description`이 `Care Point` 같은 키 변환이고 `examples=[]`. 시드는 새 유형만 삽입해 설명 갱신이 반영되지 않는다. 에이전트 계약도 예시 몇 개뿐이다. |
| F2 | `stable_fact`가 잡동사니 버킷이다 | 32건에 과거 경력, 습관·생활 패턴, 성격 자기서술, 과거 사건 회고, 서비스 계정 정보, 사용자 자신의 현재 상황이 섞여 있다. 활성 프로필 사실은 12건뿐이고, 과거 직장처럼 프로필 사실(`job` + 종료 시점)로 표현할 정보가 관찰로 저장된다. |
| F3 | `caution`이 성격이 다른 주장을 함께 담는다 | 21건에 제3자가 보고한 사건, 사용자의 예상·추측, 사용자의 입장·의도, 제3자의 평가가 섞여 있다. `care_point`와의 경계도 불명확해, 안전과 관련된 무거운 내용이 일반 배려 항목과 같은 유형에 있다. |
| F4 | `relationship_pattern`이 원자성을 어긴다 | 평균 120자, 최대 336자. 여러 달에 걸친 추론 종합이 많고, 기간이 시간 필드가 아니라 본문에 들어 있다. 교체된 기록 11건으로 가장 자주 바뀐다. |
| F5 | `preference`에 취향이 아닌 것이 섞인다 | 미래 바람("해 보고 싶다"), 특정 장소에 대한 평가, 식사 습관 |
| F6 | 주장의 형태(상태/사건/예상/의도/평가)를 구분할 축이 없다 | 같은 주제 안에서 사실·예상·의도가 구분되지 않는다. 불확실한 미래 계획을 현재 사실로 쓰지 말라는 규칙을 데이터로 지킬 수 없다. |
| F7 | 참여자 역할 정의가 서로 어긋난다 | 레지스트리는 `target`, `mentioned`를 legacy로 표시하지만, 쓰기 스키마는 7개 역할을 모두 허용하고 에이전트 계약은 `target` 사용을 권장한다. save-first 이후에도 legacy 역할 링크가 7건 생겼다. |
| F8 | 참여자 정보가 비어 있거나 모호하다 | 활성 관찰 111건(46%)에 참여자 링크가 없다. 링크 132개 중 72개가 의미가 약한 `related`다. `subject`·`about`·`target`·`related`의 경계가 정의되지 않았다. |
| F9 | 평가·예상의 보유자를 표현하기 어렵다 | "A가 B를 이렇게 평가한다" 같은 주장에서 평가자(A)가 본문에만 있다. 관점 주체 필드는 관계 평가(`relationship_assessment`)에만 있다. |
| F10 | 시간 정보가 거의 비어 있고 정밀도가 없다 | `occurred_at` 18건(7.5%), `valid_from` 1건, `valid_to` 0건. 관찰·관계·프로필 사실의 시간은 정확한 시각만 저장할 수 있어서 "작년", "올해 3월"을 표현할 수 없다. 생일 값만 부분 날짜를 지원한다. `recent_interaction`이라는 이름은 시간이 지나면 틀린 이름이 된다. |
| F11 | 프로필 사실 경계가 중복된다 | `birth_date`와 `birthday`가 둘 다 지원 상태다. `organization`·`job`·`role`의 경계 정의가 없고, 학력 유형이 없다. 구조화 검증 경로가 둘이다(이전 경로는 생일 전체 날짜만, v2는 부분 날짜 허용). |
| F12 | `confidence`가 정보를 거의 주지 않는다 | 유형별 평균이 0.80–0.92로 비슷하고, 뜻(추출 확신도인지 사실 확률인지)이 정의되지 않았다. |
| F13 | legacy 잔재가 에이전트 조회에 노출된다 | 퇴역한 `sensitivity` 레지스트리 3건이 시드에 없는데도 활성 상태다. `/api/ontology`가 `ai_use_policy`·`claim_type`·`candidate_type`을 함께 반환한다. 에이전트 계약에는 D05와 어긋나는 "schedules" 표현이 남아 있다. |
| F14 | 관계 속성이 다른 용도로 쓰인다 | `relationship_detail`에 출처 요약 문장이 들어간 사례가 있다. 근거가 `unknown`인 활성 썸 관계가 2건이다. |
| F15 | 분류기가 최신 정의를 받지 못한다 | 관계 온톨로지 조사 당시 Hermes 분류기는 레지스트리의 정의 메타데이터를 쓰지 않았다. 관찰 정의를 만들어도 분류기가 실시간으로 읽지 않으면 효과가 없다. |

## 2. 목표 모델

관찰 하나는 독립적으로 정정할 수 있는 주장 하나이며, 다음 축을 서로 독립적으로 가진다.

```text
subject_entity_id   이 기억을 누구의 맥락으로 조회할 것인가 (주로 내용이 관한 상대)
observation_type    무엇에 관한 내용인가 (주제)
assertion_mode      어떤 형태의 주장인가 (상태·성향·사건·예상·의도·평가)        ← 2단계 신설
claim_basis         출처에서 들은 것인가, 추론인가, 불명인가                    (기존)
participants        말한 사람·보유자·대상·관련 인물                             (1단계 정리)
time + precision    사건 시점·유효 기간과 그 정밀도                             ← 2단계 신설
```

`subject_entity_id`의 의미는 바꾸지 않는다. 사용자의 감정이 상대에 관한 것이면 subject는 그
상대이고, 사용자는 `experiencer`로 연결한다(현행 계약 유지). subject를 "문법적 주어"로 바꾸는
대안은 채택하지 않는다. 바꾸면 사용자 감정 21건 등 상당수 기록이 `self` 아래로 모이고, 검색이
subject 기준으로 묶여 상대의 맥락에서 빠진다.

## 3. 1단계 — 정의와 검증의 정합

### 3.1 `observation-v1` 정의 레지스트리

- `relationship_ontology.py`의 `EDGE_DEFINITIONS`처럼 관찰 유형 정의를 코드 한 곳에 둔다.
  항목: 한국어 표시명, 정의, 포함/제외 기준, 예시, 허용 `assertion_mode`(2단계), 권장 참여자 역할,
  사람 상세 카드에서의 구역.
- 버전 `observation-v1`을 `/api/ontology`, `/api/ontology/observation-types`,
  `/api/system/config.ontology`에 노출한다.
- 시드가 기존 유형의 표시명·정의도 갱신하도록 고친다(현재는 새 유형 삽입만 한다).
  과거 기록은 다시 쓰지 않는다.
- 에이전트 계약은 유형 목록을 따로 들고 있지 않고 API 정의를 단일 기준으로 가리킨다.

### 3.2 참여자 역할 정리

새 쓰기에서 지원하는 역할은 네 개로 정리하고, 각 역할의 정의를 레지스트리에 둔다.

| 역할 | 정의 | 상태 |
| --- | --- | --- |
| `speaker` | 출처에서 이 내용을 말하거나 쓴 사람(사용자 포함) | 지원 |
| `experiencer` | 감정·평가·예상·의도를 가진 사람(주장의 보유자) | 지원 |
| `target` | 행동·발언·감정·평가가 향한 대상 | 지원(legacy 표시 해제) |
| `about` | 그 밖에 내용에 등장하는 관련 인물 | 지원 |
| `related`, `mentioned`, `subject` | 이전 기록 조회용 | legacy: 읽기 가능, 새 쓰기 거절 |

- 쓰기 스키마의 역할 목록을 고정된 Literal 대신 레지스트리에서 읽는다. legacy 역할로 새로 쓰면
  관계 유형과 같은 방식으로 422와 새로고침 안내를 반환한다. 기존 기록을 정확히 보존하는
  정정은 허용한다.
- 에이전트 계약 규칙: 본문에 subject 외의 사람이 나오거나, 사용자가 말한 사람이거나 보유자이면
  해당 역할 링크를 붙인다. 이 조건은 코어가 의미로 검증할 수 없으므로, 참여자 링크가 없는 관찰
  목록을 진단 API로 노출한다.

### 3.3 legacy 정리와 용어 정의

- 시드에 없는 `sensitivity` 레지스트리 행을 비활성화한다.
- `/api/ontology`의 `policies`는 한 버전 동안 `deprecated` 표시와 함께 유지하고, 다음 버전에서
  `/api/ontology/policies` 전용 조회로만 남긴다.
- `confidence` 정의: "기록자가 원문에서 이 주장을 정확히 뽑아내고 해석했다고 보는 정도. 사실일
  확률이 아니다." 저장된 값은 바꾸지 않는다.
- 에이전트 계약 표의 "schedules"를 "이미 일어난 일·진행 중인 사안"으로 고친다.
  `relationship_detail`에 출처 요약을 쓰지 않는다는 규칙을 추가한다.

### 3.4 원자성 보조 검증

- 새 관찰 `content`의 길이를 300자로 제한한다. 기존 기록은 영향받지 않는다.
- 기간을 본문에 쓰지 말고 시간 필드를 쓰도록 계약 예시를 추가한다.

### 3.5 에이전트 연동

- Hermes 분류기가 세션 시작 시 관찰·역할 정의를 실시간으로 읽고, 버전이 바뀌면 캐시를 폐기하며,
  422를 받으면 정의를 새로고침하게 한다.
- 외부 설치본 수정·활성화는 저장소 변경과 별도로 검증하고 보고한다(relationship-v1과 같은 방식).

## 4. 2단계 — 구조 개편

### 4.1 주장 형태 축 `assertion_mode`

| 값 | 뜻 | 규칙 |
| --- | --- | --- |
| `state` | 현재의 상태·처지·사실 | 유효 기간이 있으면 `valid_from/valid_to` |
| `trait` | 지속적인 성향·습관·취향 | |
| `event` | 특정 시점에 이미 일어난 일 | 알려진 경우 `occurred_at` + 정밀도. 미래 일정은 받지 않는다(D05). |
| `expectation` | 예상·추측·우려 | `experiencer`(보유자) 필수. 현재 사실로 승격하지 않는다. |
| `intention` | 의도·계획·바람 | `experiencer` 필수. 프로필 사실로 확정하지 않는다. |
| `evaluation` | 누군가의 평가·판단 | `experiencer` 필수. 평가 대상은 subject 또는 `target`. |

- `observations.assertion_mode` 열을 추가한다(nullable). 기존 행은 `null`(미분류)로 두고 추측해서
  채우지 않는다.
- 새 메모리 쓰기 계약은 버전 `3`이다. v3에서는 일반 관찰 쓰기에 `assertion_mode`가 필수다.
  v2 요청은 전환 기간 동안 받되 `null`로 저장하고, 미분류 개수를 진단에 노출한다.
- 관계 평가는 M8의 별도 `relationship_assessments` 모델로 저장한다. 의미상 평가이고 보유자는
  보호된 Self이지만, 일반 관찰의 `assertion_mode`나 추가 `experiencer` 링크를 요구하지 않는다.
  전환 기간의 기존 `observation_type=relationship_assessment` 요청·응답은 호환 어댑터가
  처리한다. 과거 기록을 읽거나 같은 계약으로 정정할 수 있어야 하며, 새 관찰 테이블에 평가를
  다시 생성하지 않는다. 과거 `observations:<id>` 참조, 원래 평가 시각과 저장 시각,
  정정 토큰·근거·계보·미설정 null의 보존은 공통 기록 계약과 M8의 수용 기준을 따른다.
- 각 관찰 유형은 허용 형태를 정의에 둔다(예: `preference`는 `trait|state`).
  허용되지 않은 조합은 422다.

### 4.2 관찰 유형 재정비

| 유형 | v1 정의 | 변경 |
| --- | --- | --- |
| `preference` | 취향·관심사·좋아하거나 싫어하는 것 | 바람은 `intention`, 장소·대상 평가는 `evaluation`으로 분리 |
| `communication_preference` | 연락·대화 방식에 대한 선호 | 유지 |
| `trait` (신설) | 성격·습관·생활 패턴 | `stable_fact`에서 분리 |
| `life_context` (신설) | 현재 처지·상황·진행 중인 일 | `stable_fact`에서 분리. 사용자 자신의 상황은 subject=`self` |
| `recent_interaction` | 상호작용·일어난 일(`event`). 표시명을 "상호작용·사건"으로 변경 | 키는 호환을 위해 유지. 제3자가 보고한 사건도 여기에 둔다 |
| `caution` | 대할 때 피하거나 조심할 말·행동·주제 | 사건 자체는 `recent_interaction`, 예상은 `expectation` 형태로 구분 |
| `care_point` | 배려가 필요한 사정(건강·심리·생활의 어려움, 안전 관련 포함) | 정의를 명확히 함 |
| `user_feeling` | 사용자의 감정·입장 | 사용자의 입장·의도 표현 포함, `experiencer=self` |
| `follow_up_context` | 나중에 이어서 확인하거나 챙길 사안 | 일정·알림이 아님을 명시 |
| `relationship_pattern` | 두 사람 사이에 반복되는 상호작용 양상 | 원자 단위로 쓰고 기간은 시간 필드에 둔다 |
| `relationship_assessment` | 나의 관계 평가 네 축 | 의미·네 축은 유지. M8 별도 테이블로 이동하고 기존 관찰 표현은 읽기·쓰기 계약의 호환 어댑터에서만 유지 |
| `stable_fact` | — | legacy: 읽기 가능, 새 쓰기 거절 |

프로필 사실 경계:

- 직업·소속처럼 프로필로 표현할 수 있는 정보는 관찰이 아니라 프로필 사실로 저장한다.
  과거 경력은 `job`/`organization`에 `valid_to`(정밀도 포함)를 붙인다.
- `job`은 직업·직무, `role`은 조직 안의 직책, `organization`은 소속 조직명으로 정의한다.
- `education`(학교·전공) 사실 유형을 추가한다.
- `birthday`는 legacy로 돌린다. 연도 없는 생일은 `birth_date`가 받도록 정밀도 규칙을 넓힌다.
  라이브의 활성 `birthday`는 0건이다.
- 프로필 검증을 v2 정규화 경로 하나로 통일한다.

### 4.3 시간 정밀도

- 관찰·관계·프로필 사실의 지원하는 시간 필드(`occurred_at`, `valid_from`, `valid_to`)마다
  정밀도(`year|month|day|datetime`)를 보존한다. 부분 날짜는 정확한 사건 시각이 아닌 불확실한
  시간 구간이다. 구간 경계 계산·시간대·현재 판정은 공통 기록 계약 하나를 따른다.
  내부 정렬용 구간 시작값을 저장하더라도 실제 발생일이나 확정 유효기간 경계로 해석하지 않는다.
  표시는 원래 정밀도대로 한다("2025년", "2026년 3월").
- 쓰기 입력은 정확한 시각(정밀도 `datetime`) 또는 생일과 같은 부분 날짜 객체
  `{year, month, day, precision}`를 받는다.
- 상대 날짜("작년", "지난달")는 출처 발화 시각이 있을 때만 그 정밀도로 환산한다.
  모르는 날짜는 `null`로 두고, 일(day)을 만들어 넣지 않는다.
- `valid_to="2026년 3월"`은 3월 중 종료라는 불확실성을 유지한다. 3월 1일을 확정 종료로 간주해
  조기 종료하지 않는다. 해당 구간 안에서는 공통 계약의 불확실 판정·표시를 적용하고, 목록·상세·
  context card·검색·Context Pack이 같은 판정을 사용한다. revision 상태를 종료 시각 때문에
  `superseded`로 바꾸지 않는다.
- 기존 정확한 timestamp와 시간대는 손실 없이 보존한다. 정밀도 `null`은 이전 기록에 명시적인
  정밀도 선언이 없다는 뜻이며, timestamp를 자정으로 자르거나 날짜만으로 되쓰지 않는다.
  축약 표시를 하더라도 원래 시각을 상세 조회와 API에서 확인할 수 있어야 한다.
- 검색의 최근성은 공통 계약의 구간 규칙에 따라 보수적으로 산정하고, `year` 정밀도는 가산에
  쓰지 않는다. 계산에 쓴 경계는 scoring 근거이지 실제 발생일이 아니며 원본을 바꾸지 않는다.

### 4.4 화면·조회

- 기억 목록에 형태 필터와 형태 배지를 추가하고, 편집기에 형태 선택과 부분 날짜 입력을 추가한다.
  역할 표시명은 레지스트리 정의를 쓴다.
- 사람 상세와 context card의 구역은 정의의 `card_section`을 따른다. 현재 하드코딩된
  `communication_preference`·`caution` 분기를 정의 기반으로 바꾼다.
- 검색과 Context Pack은 `assertion_mode`와 정밀도를 함께 내보낸다. `expectation`·`intention`은
  숨기지 않고 형태를 표시한다.

### 4.5 v2/v3 클라이언트 전환 (2026-10-22)

- 현재 웹의 strict `contract_version="2"` 검증과 Hermes의 실제 송수신 버전을 함께 확인한다.
  서버가 먼저 v2/v3를 병행 지원하고 지원 버전을 알린다. v2 요청에는 호환되는 v2 receipt를,
  v3 요청에는 v3 receipt를 반환하며, 기존 request-id 재실행은 원래 receipt·버전을 보존한다.
- 이후 웹의 런타임 응답 검증·편집기·정정/재시도 경로를 v3에 맞추고 실제 브라우저에서 검증한다.
  Hermes도 정의 조회·형태 작성·역할 검증·정정 경로를 v3로 전환하고 설치된 실행 코드로 확인한다.
  저장소 helper 수정이나 새 정의 API만으로 클라이언트 전환을 완료 처리하지 않는다.
- v2 일반 관찰의 형태는 null이고, v3 일반 관찰은 형태가 필수다. v2에서 v3로 읽기만 했다는
  이유로 기존 형태를 추정하지 않는다. 평가 호환 어댑터에는 일반 관찰 필수 형태 검증을 적용하지 않는다.
- 새 쓰기의 legacy 유형·역할 금지(OV02)는 계약 버전으로 우회하지 않는다. 소비자가 새 정의와
  오류를 처리할 수 있도록 준비한 뒤 금지를 활성화하고, 기존 정확한 구조의 정정 예외는 유지한다.
- 웹과 Hermes를 포함한 모든 실제 writer가 v3를 쓰는 것이 확인되고 전환 종료가 정해지기 전에는
  v2를 종료하지 않는다. 읽기·기존 receipt 재실행 호환은 신규 v2 쓰기 종료와 별도로 유지한다.

## 5. 기존 데이터 전환

### 5.1 원칙

- 기존 `MemoryMigrationService`의 가드된 manifest 방식(원본 보존, 근거 복사, 변경 이력, dry-run,
  재실행 멱등성)을 확장해 쓴다. manifest는 개인 내용을 담으므로 저장소 밖에 둔다.
- 유형 변경·분할·프로필 사실로 이동은 교체(replacement)로 처리하고 원본은 superseded로 남긴다.
  관찰→사실의 교차 유형 이동과 한 관찰→여러 주장 분할은 공통 기록 계약의 1:N 계보로 연결한다.
  같은 테이블의 단일 self-FK로 축약하지 않으며 원본 identity·출처·이력 참조를 보존한다.
  형태 지정, 역할 추가·교체, 시간 정밀도는 metadata 항목으로 처리한다. 현재 metadata는 링크
  추가만 지원하므로 "legacy 링크를 새 역할로 대체" 연산을 추가한다.
- 원문과 근거로 확인되는 것만 바꾼다. 모호하면 `assertion_mode=null`, `related` 링크 유지,
  유형 그대로 둔다. 인용·날짜·평가자·근거를 만들어 넣지 않는다.
- 일괄 규칙 변환을 금지한다. 레코드마다 판정 근거를 manifest에 남긴다.
- 교체로 새로 생긴 관찰은 임베딩 대기 상태가 되며, 자동 인덱싱 또는 백필로 다시 만든다.

### 5.2 대상 규모 (2026-10-19 기준, 전환 직전에 다시 집계)

| 대상 | 건수 | 처리 |
| --- | --- | --- |
| 활성 `stable_fact` | 32 | 개별 판정: 프로필 사실, `trait`, `life_context`, `recent_interaction`(event) 중 하나로 교체, 또는 유지 |
| 활성 `caution` | 21 | 사건/예상/입장/평가를 구분해 유형·형태 지정 |

| 활성 `preference` | 38 | 바람·평가·습관을 분리 |
| 참여자 링크가 없는 활성 관찰 | 111 | 본문이 사람을 특정하는 경우에만 역할 추가 |

### 5.3 절차

1. 일관된 DB 백업을 만들고, 격리된 복사본에 복원해 검증한다.
2. 복사본에 스키마 마이그레이션을 적용한다.
3. 레코드별 manifest 초안을 작성한다. 판정마다 근거 문장을 붙이고, 모호한 항목은 별도 목록으로
   둔다.
4. **사용자 검토:** 개인 기록의 재해석이므로 manifest 요약과 모호 목록을 사용자가 확인한다.
5. 복사본에서 dry-run과 실제 적용, readback을 한다(레코드 수·근거 연결·이력·context card·검색).
6. 라이브 적용은 별도 승인 후 진행하고, 적용 후 같은 readback과 manifest 대조를 반복한다.

## 8. 실행 단위

1. **PR A — 1단계:** 정의 레지스트리, 역할 정리, 검증, legacy 정리, 계약 문서. 스키마 변경 없음.
2. **PR B — 2단계 스키마·API:** 공통 기록 계약과 M8 연계, 형태 축, 시간 구간·정밀도, v2/v3 병행 계약, 조회·진단, 사실 유형 정리.
3. **PR C — 화면:** 형태·정밀도 입력과 표시, 정의 기반 카드 구역, strict version 검증과 v3 정정/재시도 전환.
4. **PR D — 전환 도구:** manifest 확장과 리허설 스크립트.
5. **라이브(각각 별도 승인):** 복사본 리허설 → v2/v3 호환 서버 배포 → 웹·Hermes 갱신과 실제 writer 검증 → manifest 검토 → 라이브 전환 → v2 신규 쓰기 종료 판단. 기존 운영 이력의 승인 범위를 확대하지 않는다.
