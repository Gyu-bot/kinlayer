## 관계 정의와 데이터 범위

정식 타입과 방향은 서버 정의 및 라이브 레지스트리가 단일 기준이다. 지원 범위는
[온톨로지 정의의 관계 표](../specs/ontology-design.md#8-relationship-v1-meaning-and-compatibility)에
기록한다. 새 클라이언트 enum을 복제하지 않는다. 모든 관계의 두 끝점은 사람이며 사용자 자신이
반드시 포함될 필요는 없다. 출처가 뒷받침하면 같은 두 사람 사이에 여러 관계가 함께 존재할 수 있다.

관계의 선택 속성은 `context`(회사·학교·모임), `relationship_detail`(구체적 친족·관계 설명),
`origin`(알게 된 경위)이다. 각 값은 비어 있지 않은 300자 이하 문자열이며 다른 키는 거절한다.
알게 된 경위만으로 더 강한 관계를 만들지 않는다. 감정·주의점·해석은 기존 observation에
주체와 참여자 역할, 근거를 보존한다. 새 일정/만남 타입은 추가하지 않는다.

방향형 관계는 부모→자녀, 부하→상사, 고객→서비스 제공자, 선배→후배, 교사→학생,
멘토→멘티로 정의한다. 양 끝점 관점의 표시명은 서버 `label`/`inverse_label`을 이용한다.
별도 역방향 edge를 자동 생성하지 않는다. `former_coworker`, `former_partner`,
`former_spouse`처럼 현재도 유용한 과거 관계 유형은 유지한다.

기존 모호한 타입은 읽을 수 있는 legacy로 남기고 새로운 쓰기만 막는다. `active`와
`write_supported`는 다른 의미다. `replacement_type`은 자동 변환 지시가 아니다.
정확한 기존 구조를 유지한 문장·출처·시간 정정은 허용하지만, 새 legacy edge를 만들거나
다른 사람에게 legacy 구조를 재귀속하는 예외로 확장하지 않는다.

## 기존 데이터 전환 원칙

1. 현재 원문·출처·끝점·속성과 기존 이력을 읽고 변환 전 상태를 고정한다.
2. 의미가 확인되는 레코드만 명시적 manifest로 교체한다. 모호함을 없애기 위해 정보를 만들지 않는다.
3. 원본은 보존하고 교체 이력과 기존 근거를 연결한다. 표현 변환으로 과거 기록을 최근 사건처럼 만들지 않는다.
4. dry-run과 실제 readback에서 레코드 수, 근거 보존, 방향, 현재 context와 graph 노출을 확인한다.
5. 코드·정의 배포와 실제 데이터 변환 결과는 구분해서 보고한다. 자동 시작 seed가 원문을 해석하거나
   모든 과거 레코드를 임의로 변환해서는 안 된다.

## 에이전트 배포와 남은 연결 작업

`GET /api/ontology`와 `/api/ontology/edge-types`는 `relationship-v1` 및 표시명, 방향,
역방향 표시명, 정의·예시, 속성 스키마, 지원·쓰기 상태, 교체 힌트를 제공한다.
저장소 helper는 기존 `values`/`counts`와 함께 `version` 및 전체 `definitions`를 보존한다.
타입 이름만 받은 에이전트가 뜻을 추측하도록 하지 않는다.

에이전트는 세션 시작과 모르는 타입 사용 전에 레지스트리를 읽고, API 인스턴스별 버전이 바뀌면
캐시를 폐기한다. 타입·방향·속성 검증 오류에서는 새로고침한 뒤 출처와 정의를 다시 대조한다.
검증을 통과시키려고 이름이나 사람의 방향, 주장의 뜻을 바꾸면 안 된다.

이번 조사에서 외부에 설치된 Hermes `personal-context-router`는 `router/post_turn.py`의
레지스트리 필터가 `active`만 읽고 `write_supported`/`support_level`을 구별하지 않으며,
`hooks.py`의 분류 지침은 실시간 관계 정의를 분류기에 제공하지 않는 것으로 확인되었다.
설치된 `kinlayer-local` skill은 저장소 helper를 참조하지만 이것만으로 runtime 분류 코드가
업데이트되지는 않는다. 설치된 plugin/skill 수정과 실행 세션 새로고침은 별도 연결 작업이다.
저장소 문서 수정, 외부 패치 준비, 설치·활성화, 실제 새 버전 조회를 각각 검증하고 구분해 보고한다.
이 문서는 외부 에이전트에 알림을 보냈거나 설치본을 이미 변경했다는 의미가 아니다.

| 외부 Hermes 패치 | 비공개 복사본에서 네트워크 차단 합성 테스트 66개 통과. 설치된 plugin/skill에는 미적용. |
| 라이브 적용 | 미배포. 기존 데이터 전환과 외부 실행 세션 활성화를 완료한 것으로 간주하지 않는다. |

통합 검토에서 발견한 과거 지원 유형의 방향 보존 문제도 수정했다. 기존 `friend`처럼 지금은
대칭인 유형이 과거 방향형으로 저장되었더라도, 문장만 정정하면 방향과 기존 속성을 그대로
보존한다. 해당 회귀 테스트를 포함한다.

라이브 데이터는 조회만 했다. 선택된 API 레코드를 비공개 SQLite에 복원한 전환 리허설에서
dry-run rollback, 원문·기준·시각·기존 근거 연결 보존, 재실행 멱등성을 확인했다. 이는 운영 DB
백업이나 실제 전환 결과가 아니다. 일부 이전 유형은 연결된 원출처가 없으며, API의 출처 누락
표시를 근거로 취급하지 않는다. 모호한 기존 기록은 실제 의미를 확인하기 전까지 그대로 보존한다.

## D09 제안 — 사용자 관점의 관계 프로필

**제안이며 구현 미승인이다.** 친구·동료·가족 등 관계 종류와 별도로, 사용자 자신이 상대와의
관계를 어떻게 보고 있는지 self→person 단위로 표현한다. 상대의 전역 프로필 사실도 아니고,
친구·동료 등 각 edge에 반복 저장하는 속성도 아니다. 제3자가 보는 친밀도나 상대의 감정을
대신 나타내지 않는다.

| 독립 축 | 제안 선택값 | 뜻 |
| --- | --- | --- |
| 친밀도 `closeness` | 얼굴만 앎 / 가벼운 지인 / 편한 사이 / 가까움 / 매우 가까움 | 사용자가 느끼는 관계의 가까움. |
| 중요도 `importance` | 보통 / 중요 / 매우 중요 | 사용자에게 이 관계가 갖는 중요도. |
| 교류 빈도 `interaction_frequency` | 자주 / 가끔 / 드묾 / 없음 | 사용자가 설명한 평소 교류 빈도. 횟수·만남 기록을 집계하는 기능이 아니다. |
| 연결 상태 `connection_state` | 유지 / 소원 / 단절 | 사용자가 설명한 현재 관계의 이어짐 상태. |

모든 축의 기본값은 **미설정**이다. 미설정은 ‘얼굴만 앎’, ‘보통’, ‘없음’, ‘단절’ 등 가장 낮거나
부정적인 값과 다르다. 네 축은 독립적이다. 교류가 드물어도 가까운 사이일 수 있고, 중요하지만
가깝지 않을 수 있다. 기록이 없거나 오래되었다는 이유로 자동 하향·소원·단절 처리하지 않으며,
교류 빈도로 친밀도를 추론하지 않는다.

저장 설계도 제안 단계다. 각 축을 **독립적으로 정정 가능한 주장**으로 저장하고, 사용자와
상대의 ID를 기준으로 현재 주장들을 모아 관계 프로필을 보여주는 방식을 권장한다. 축마다
출처, 알려진 평가·적용 시점, 변경 이력을 보존하고 이후 대화로 해당 축만 정정할 수 있어야 한다.
이때 저장 시각을 평가 시각으로 꾸미지 않는다. 임의의 edge properties에 네 값을 추가하거나,
같은 두 사람 사이의 여러 관계마다 복제하지 않는다. 구체적 테이블·API는 구현 승인 이후 정한다.

화면은 사람 상세의 ‘나와의 관계’ 프로필과 목록의 요약 칩·축별 필터를 제안한다. 에이전트에는
각 값과 사용자 관점, 출처·시점을 함께 전달한다. 중요도는 관련 문맥 선택의 보조 우선순위로만
사용하고, 사실의 신뢰도나 관계 종류를 바꾸거나 덜 중요한 관계를 차단하는 기준으로 사용하지
않는다. 이 제안에도 만남·약속·일정·캘린더·알림 로그를 추가하지 않는다.

## 별도 승인 전 보류
